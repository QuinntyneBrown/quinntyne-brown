ROLES, ORGANIZATIONS AND PERMISSIONS
====================================
A plain-language guide to who can see and do what.
Source of truth: the server (Application/Organizations/AccessResolver.cs,
Application/*Access.cs and docs/adr/, especially ADRs 0033 to 0041). The
app only hides buttons; the API refuses anything you may not do.


1. THE BASICS
-------------
- Everyone signs in with ONE profile. Profiles are global: one per person.
- A person belongs to zero, one or several ORGANIZATIONS ("orgs").
- Every record (event, partner, contact, resource, note page, workspace,
  announcement, invite, connect link) belongs to exactly ONE org.
- You see the data of the orgs you COVER: the orgs you are a member of,
  plus any orgs a cross-org role or the Portfolio Lead tier gives you.
- Roles are held PER ORG. Several roles = the union of their powers.
- If something is outside your coverage, the server says "not found" (404).
- Exception that never bends: PRIVATE items (private contacts and their
  notes, private resources, private note pages) are seen only by their
  owner and System Admin (audited).


2. THE HIERARCHY
----------------

  SYSTEM ADMIN (platform)          anything, anywhere; opening someone's
     |                             private item or overriding is audited
     |
  PORTFOLIO  "Quinntyne Brown"     data; more portfolios are possible
     |-- PORTFOLIO LEAD            built in: anything in every org of the
     |                             portfolio except other people's private
     |                             items; edits Org Types, catalogues,
     |                             feature flags and cross-org roles
     |-- CROSS-ORG ROLES           data: a permission bundle over a set of
     |     "Portfolio"             orgs, every org of a type, or the whole
     |     "Staff"                 portfolio
     |
     |-- ORG TYPE (data)           a role catalogue + enabled features
     |     "FaithTech City"        every feature
     |     "Startup"               profiles, invites, notes, resources, agile
     |
     |-- ORGANIZATION (data)       "FaithTech Toronto" (FaithTech City)
           |                       "Shelfie" (Startup)
           |-- ORG LEAD            built in, every org: anything in the org
           |                       except other people's private items
           |-- catalogue roles     from the org's type (below)
           |-- MEMBER              built in: in the org, no role

  The tree inside a catalogue is only display order. Power comes ONLY from
  each role's permission list and its "can grant" list. Nothing is inherited
  from a parent role.

4. PERMISSION CODES (fixed in code)
-----------------------------------
  people.view            the People page with roles
  roles.grant            change roles (only those in the role's CanGrant)
  invites.send           invite people into the org
  connectLink.own        a reusable QR code for the org
  contacts.private       keep your own private contacts in the org
  partners.read/.write   read / change the partner pipeline
  events.manage          create, edit, cancel events
  events.rsvpList        see who RSVP'd and the check-in page
  events.rsvpListEmails  guest emails and the RSVP export
  events.checkIn         check people in, walk-ins, attendance export
  announcements.send     send announcements to the org
  resources.create       add resources
  notes.create           create note pages
  workspaces.create      create and own workspaces
  workspaces.join        can be added to the org's workspaces
  workspaces.readAll     read every workspace of the org
  reports.view           the Reports page for the org
  team.member/team.lead  listed on the Team page / matches its Leads filter

  Each code belongs to a feature. If the org's type switches a feature off,
  its codes grant nothing there and its pages and endpoints are "not found".

6. WHO GIVES OUT ROLES
----------------------
  SYSTEM ADMIN    --> System Admin, Portfolio Lead (and anything below)
  PORTFOLIO LEAD  --> Org Lead, cross-org roles, any catalogue role in its
                      orgs
  ORG LEAD        --> any catalogue role in its org
  CATALOGUE ROLE  --> only the roles in its "can grant" list, only in its
                      own org (FaithTech City: City Lead grants the other six)
  Everyone else   --> cannot change roles

  - When an Org Lead or a catalogue role changes your roles, you are
    notified. Portfolio Lead and System Admin changes go in the audit log.
  - An invite can come with a role pre-assigned (same limits apply).
  - Only the Portfolio Lead (or System Admin) edits Org Types, catalogues,
    feature flags and cross-org roles. Every edit is audited, before and
    after. A role somebody holds cannot be removed from a catalogue.
  - Changes take effect on your next request.


7. CROSS-ORG ROLES
------------------
  A cross-org role applies a permission list across:
    - a list of orgs, or
    - every org of a type (new orgs of that type are covered at once), or
    - the whole portfolio.
  An assignment can narrow it to fewer orgs.

  PORTFOLIO   whole portfolio. Reads everything in covered orgs (profiles,
              partners, events and RSVP lists, workspaces, org-wide and
              shared items, reports) except private items. Can be added to
              workspaces and assigned work (CanJoinWork). Manages nothing.
  STAFF       every FaithTech City org. Reads nearly everything (partners,
              people, events, every workspace, reports); changes only their
              own resources and note pages. Never sees private contacts.


8. JOINING AN ORG
-----------------
  - Through that org's INVITE (expires after 14 days) or CONNECT LINK
    (a QR code that never expires and can be replaced; one per person per
    org), or by being ADDED by the Org Lead or the Portfolio Lead.
  - Signing up with no link: you belong to no org and see "Waiting to be
    added" until someone adds you.
  - Leaving or being removed: your roles in that org go; things you own
    stay in the org. Workspaces you owned get a new owner.


9. WORKSPACES (AGILE)
---------------------
  A workspace belongs to one org.

  Who creates one?   workspaces.create holders (City Lead in FaithTech),
                     the Org Lead or the Portfolio Lead. The creator is OWNER.
  Who can be added?  org members with workspaces.join, plus cross-org role
                     holders with CanJoinWork. Not suspended.

     OWNER  ......... the creator (or whoever it was given to)
     ADMIN  ......... the org's Org Lead, the Portfolio Lead, System Admin
     MEMBER ......... someone the owner added
     READ-ONLY ...... workspaces.readAll holders (e.g. Staff)
     OUTSIDER ....... everyone else: cannot see it exists (404)

                             Owner  Admin  Member  Read-  Outsider
                                                   only
  See the workspace           yes    yes    yes     yes     no
  Stories, tasks, comments,   yes    yes    yes     no      no
   move cards, sprint
   planning, Planning Poker
  Initiatives & epics,        yes    yes    no      no      no
   rename, members, sprints,
   switch Kanban/Scrum,
   archive & restore
  Reassign the owner          no     yes    no      no      no

  - If an owner loses workspaces.create in the org (or leaves it), the Org
    Lead and Portfolio Lead are told it "needs a new owner"; either can
    reassign it. The old owner stays as a member if still eligible.


10. RESOURCES AND NOTE PAGES (VISIBILITY)
-----------------------------------------
    PRIVATE         -> only the owner (and System Admin, audited)
    SHARED          -> owner + named people + holders of a named role in the
                       item's org (or a named cross-org role covering it)
    ORG-WIDE        -> everyone who covers the item's org (was "Global")
    PORTFOLIO-WIDE  -> everyone in any org of the portfolio; only the
                       Portfolio Lead can choose it

  - New resources default to ORG-WIDE. New note pages default to PRIVATE.
  - Only the OWNER edits, shares, archives or restores. System Admin can
    override (audited).
  - Archived resources are purged after 30 days. Archived note pages stay.


11. FEATURES PER ORG TYPE
-------------------------
  profiles and notes are always on. contacts, partners, team, events,
  announcements, invites, resources, agile and reports can be switched off
  per Org Type. Switched off = gone from the menu and "not found" on the
  server, for everyone in those orgs.


12. AGENTS
----------
  An agent is a profile marked "Agent": no password, no email sign-in.
  It calls the API with a token the Portfolio Lead (or an Org Lead, for
  their own org) issues: named, limited to chosen orgs, expiring in 1 to 90
  days, revocable at any time, with its last use shown. It holds roles like
  a person. Everything it writes is logged as the agent, with who issued the
  token. Agents are hidden from People unless you ask, and carry a badge.


13. ANONYMOUS VISITORS (NOT SIGNED IN)
--------------------------------------
  - Can see PUBLIC event pages only, at /o/{org}/events/{id}, with the
    org's name, logo and colour
  - Can RSVP as a guest and download the calendar (.ics) file
  - Cannot see any profile or anything else


14. GOLDEN RULES
----------------
  - More roles = the union of their powers. No inheritance.
  - The server checks permission codes, never role names.
  - Outside your coverage = "not found" (404). Covered but not allowed =
    "forbidden" (403).
  - Private stays private: only the owner and System Admin, ever.
  - System Admin can override anything; it is always audit-logged.
