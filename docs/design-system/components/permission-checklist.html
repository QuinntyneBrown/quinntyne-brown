Permission checklist

A role’s permission codes, grouped by feature, with hidden features noted.

WCAG 2.2 AAStatus: new

Overview

The permission checklist edits a catalogue role’s or a cross-org role’s permission codes, grouped by the feature each code belongs to. Groups count what’s ticked; features switched off for the Org Type are hidden, with a note saying how many and which.

Anatomy

  1. GroupA fieldset per feature, its legend the feature name.
  2. Count“{n} of {m}” ticked, in the legend so it’s read with the group.
  3. ItemA checkbox with the plain-language meaning and the code in mono below it.
  4. Hidden noteLists the features that are off and how many codes are hidden.

Checkbox hover, focus and disabled states come from Checkbox group. Invalid appears only where a bundle may not be empty (a cross-org role).

Responsive behaviour

Groups stack in one column below 1024px and flow into two columns from 1024px. Codes wrap anywhere; descriptions wrap normally.

Theming

Groups are surface cards with the default border; text and codes use the default and muted roles, so both themes work unchanged.

Accessibility

  • Each feature is a fieldset with a legend (“Events, 3 of 4”), and every checkbox is wrapped by its label, so the name is the description and the code.
  • The whole checklist is a role="group" named “Permissions by feature”.
  • Tab moves between checkboxes; Space toggles. Nothing is drag-only.
  • The hidden note is plain text after the groups, so it is read in order.

Content

  • Descriptions start with a verb (“Create, edit and cancel events”).
  • The note: “{n} permissions are hidden because these features are off for this type: {list}. Stored ones are kept but grant nothing.”

  [groups]="groups"                 // { feature, label, permissions: { code, label }[] }[]
  [value]="role.permissions"         // string[] (also a ControlValueAccessor)
  [hiddenFeatures]="['Contacts', 'Partners']"
  (valueChange)="role.permissions = $event" />
